# 用了三方 SDK 地图卡顿怎么优化

## 一句话

地图卡顿通常不是「多画了几个 marker」这么简单，要拆成：**SDK 体积与初始化时机、主线程占用、图层/标注渲染量、数据 waterfall**。三方 SDK（Google Map / Mapbox / 高德）改不了内核，就优化**怎么用、何时用、用多少**。

## 先定位卡在哪

1. **首屏卡**：SDK 本身大、同步加载、和业务 JS 抢带宽
2. **交互卡**：拖拽/缩放时 marker 过多、频繁 setState、同步算坐标
3. **数据卡**：酒店价/列表串行请求，地图等数据才画全

Performance：看 Long Task、主线程、网络瀑布。Lighthouse / Performance 面板比猜有用。

## 常见优化（按收益）

### 1. 加载与初始化

- **按需 / 动态 import**：地图组件客户端再加载；SSR 场景服务端无 `window`，hydrate 后再 `init`
- **延后非关键**：先出列表/骨架，视口进地图区域或用户点「看地图」再 init SDK
- **SDK 本身**：只用需要的库能力；能走 CDN/缓存就别打进主包重复打包

### 2. 渲染与主线程

- **marker 聚合（cluster）**：缩放级别低时合并点，避免一次上千 DOM/Overlay
- **视口裁剪**：只渲染当前 bounds 内的点，拖动结束再补
- **节流**：`move` / `zoom` 用 rAF 或 throttle，别每个 pixel 都重算业务状态
- **少强制同步布局**：批量改样式；大列表不要和地图同帧狂刷 React/Vue 更新
- **Offscreen / Worker（进阶）**：坐标换算、聚合算法可下沉 Worker，主线程只管画

### 3. 数据与架构（携程地图页同类思路）

- **SSR 预取**首屏酒店/价格，减少白屏等接口
- **BFF 批量聚合**，消灭价格/列表 waterfall
- 地图图层与业务模块拆开，避免整页因价签更新重绘地图

### 4. 体验兜底

- 弱网：降采样瓦片、先静态底图
- 失败：降级列表模式，不堵死主流程

## 项目可挂钩说法

Trip.com 酒店地图列表：React SSR + Google Map/Mapbox；瓶颈是地图资源重 + 价格 waterfall。手段是 **SSR 预取 + BFF 批量 + 客户端再 init 地图**，首屏约 4s→2s。卡顿优化和首屏优化同一套思路：**少占主线程、少串行、少一次画太多点**。
