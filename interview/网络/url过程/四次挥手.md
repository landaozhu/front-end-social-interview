## 概念

TCP 是全双工，两边各有一条发送方向。关掉连接 = 两边分别说「我这边没数据了」，所以是 **四次**，不是三次握手的镜像。

发生在 **数据已经传完、要拆 TCP 的时候**，不是输入 URL 之后立刻挥手。HTTP/1.1 keep-alive 会先复用这条连接，真正关的时候才走下面。

- **第一次**：主动关闭方（常见是客户端）发 `FIN`，表示我这边不再发数据。进入 `FIN_WAIT_1`。
- **第二次**：对端回 `ACK`，表示收到了你的 FIN。对端进入 `CLOSE_WAIT`，主动方进入 `FIN_WAIT_2`。此时对端 **还可以继续发** 自己还没发完的数据。
- **第三次**：对端也发完了，再发自己的 `FIN`，进入 `LAST_ACK`。
- **第四次**：主动方回 `ACK`，进入 `TIME_WAIT`（等一会儿，防迟到的包）；对端收到 ACK 后进入 `CLOSED`。等够 `TIME_WAIT` 后主动方也 `CLOSED`。

### 通俗的话描述

- 第一次：我说「我说完了」
- 第二次：你说「知道了」（你可能还有话要说）
- 第三次：你也说「我说完了」
- 第四次：我说「知道了」，连接拆掉

## 为什么是四次，不是三次

第二次的 ACK 和第三次的 FIN **不能合成一次**（除非对端恰好也没数据了，有些实现会合并，面试仍按四次讲）：对端收到你的 FIN 时，自己发送缓冲区里可能还有数据，必须先 ACK 你的关闭，把剩下的发完，再 FIN。三次握手是同时协商「两边都准备好传」；挥手是两边分别关发送方向，中间夹着半关闭。

## 为什么要 TIME_WAIT

主动方最后那个 ACK 如果丢了，对端会重发 FIN。主动方还在 TIME_WAIT，才能再回一次 ACK，避免对端卡在 LAST_ACK，也避免旧连接的包跑到新连接上。

## 什么时候执行（和渲染比）

**问：四次挥手跟渲染哪个先？**

答：**渲染先开始，挥手在后。** 三次握手 → 传数据 → 浏览器用收到的 HTML/CSS **开始解析和绘制** → 这条 TCP 不再传了才四次挥手。

挥手 = 关连接。关了就不能再靠它收页面。所以不可能「先挥手再渲染」。

也不是「整页渲染完立刻挥手」：

- keep-alive / HTTP/2：第一帧都画出来了，连接还留着拉后面的图和脚本，过一阵空闲或标签关了才挥手
- `Connection: close`：HTML 传完服务端可能先 FIN，此时客户端 **已经在 parse/渲染这段 HTML**，挥手和渲染可能重叠，但渲染用的数据是挥手前已经到的

记位置：三次握手在导航最前；四次挥手在这条连接的最后。中间夹着请求、响应、渲染。

## 和 URL 过程的位置

```
三次握手 → TLS → 发 HTTP → 收响应 → 解析渲染（连接仍开着）→ 四次挥手
```
