# 为什么要用 BFF 层

## 一句话

BFF（Backend For Frontend）是**为前端定制的后端**，不是再造一个业务中台。核心价值：**聚合、裁剪、适配、让前端少等后端排期**。

## 为什么需要

1. **接口聚合**：一页要 N 个微服务；前端串行/并行打 N 次 → 改成 BFF 一次返回，减 RTT、消 waterfall（地图价签、酒店列表典型）
2. **字段适配**：多端（H5 / PC / 小程序）要的形状不同；BFF 按端裁剪，避免前端到处 `map` 脏数据
3. **权限与网关靠近端**：登录态、灰度、AB、前端错误码统一包装
4. **缩短联调**：前端能改聚合和适配，不等后端大排期（猫眼 Egg 中间层同一思路）
5. **SSR 友好**：服务端渲染要一次拿齐首屏数据，BFF 比浏览器直连一堆 API 干净

## 不是什么

- 不是把所有业务规则塞进 Node/Java 中间层
- 复杂事务、强一致、库存扣减仍归领域服务
- BFF 薄：编排 + 适配；胖逻辑下沉领域层

## 和网关 / 中台区别

| | BFF | API 网关 | 业务中台 |
|--|-----|----------|----------|
| 服务对象 | **某一个前端** | 所有调用方 | 领域能力 |
| 典型活 | 聚合、DTO 转换 | 鉴权、限流、路由 | 下单、库存 |
| 变更频率 | 跟页面一起变 | 相对稳 | 稳 |

## 简历可挂钩

- **猫眼**：Egg/Koa 中间层，字段适配、草稿/默认计划，缩短联调
- **携程酒店地图**：Java BFF 做价格下沉、地图围栏批量，配合 SSR，首屏 4s→2s

一句话收束：**离前端近的一层自己掌控，专为页面交付服务。**

## 追问

- BFF 挂了怎么降级？部分酒店无价怎么办？
- 为什么有人用 GraphQL 当 BFF？和 REST 聚合怎么选？
- BFF 和前端同仓库还是独立服务，边界怎么划？
- **为什么后端要做微服务？**（和 BFF 怎么串起来）

### 答：为什么后端要做微服务

单体到一定规模会：发布耦合、团队抢同一仓库、局部故障拖垮整站、技术栈难演进。拆成微服务后，**按领域独立部署、扩缩容、容错隔离**（订单挂了搜索还能用）。

代价是：前端一页要打很多服务 → RTT 多、waterfall、字段各异。所以才需要 **BFF 做聚合/适配**——微服务解决后端协作与扩展，BFF 解决前端交付体验。两者是配套，不是二选一。
