## 先记住一件事

沙箱不是「一个开关搞定隔离」。它要同时管三件事：

| 隔离什么 | 不隔离会怎样 | 上单里的体感 |
|----------|--------------|--------------|
| JS：window 上的全局变量 | 子应用给 `window.xxx` 赋值，切走后主应用/下一个子应用还在 | store、eventBus 串台 |
| BOM：定时器、addEventListener | 子应用 `setInterval` 没清，切走后还在跑 | 内存涨、接口还在打 |
| 样式：CSS | Vue2 的 iView 和 Vue3 的 antd 类名撞车 | 按钮、弹窗样式乱 |

iframe 这三样都天然隔离，但弹窗穿不出去、URL 不同步，所以上单没用 iframe。qiankun 是在同一个页面里用 JS 模拟隔离。

## 贾顺昌那份 PPT 在讲什么（按他的目录）

整份分享就四段，不必逐页啃。

### 1. 子应用生命周期（沙箱挂在哪）

路由匹配 → 拉 html/js（HTML Entry）→ 放进沙箱里执行 → 卸载时还原

沙箱不是一直开着，而是 mount 时套上，unmount 时拆掉。你们主应用里的 `beforeUnmount` 清 eventBus，就是这个时机。

### 2. JS 沙箱：两种做法

**快照 Snapshot**

进子应用前把 `window` 拍一张照片，退出时按照片还原。

缺点：所有应用共用一个真正的 `window`，不能两个子应用同时活着。IE 或不支持 Proxy 时 qiankun 才用。

**Proxy**（分享里叫 browser-VM；Garfish 是 with + Proxy）

给子应用一个假 `window`，读写都拦下来。子应用以为在改全局，其实改的是自己那份。

这是 qiankun 现在的默认。支持多实例。

你只要能说出：**我们用的是 Proxy 假 window，不是拍快照。**

### 3. 样式隔离：Shadow DOM

PPT 里花了很多页讲 Shadow DOM。你们项目里对应这一行：

```js
start({ sandbox: { strictStyleIsolation: true } });
```

`strictStyleIsolation: true` = 把子应用塞进 Shadow DOM。主应用 CSS 进不去，子应用 CSS 也难漏出来。这就是「强隔离」。

PPT 同时写了强隔离的代价，这些才是上单会踩的：

- `document.querySelector` 找不到 Shadow 里的节点
- antd Modal / Popover 默认挂到 `document.body`，跑到 Shadow 外面，样式丢、点取消没反应
- 事件的 `event.target` 指向会怪

你们 bug 里的 popover 取消不了、弹窗居中，就是这一类，不是「antd 我不会用」这么简单。

### 4. 沙箱会逃逸（PPT 原话）

- 只隔离 `window` 上的一层属性。`window.a.b = 1` 这种改对象内部，Proxy 拦不住。
- 绑在 `document.body.onxxx` 上的事件，沙箱不管，必须自己在 unmount 里拆。
- qiankun 另外劫持了 `setTimeout` / `setInterval`、动态插入的 `style`/`link`，卸载时清掉、还原。

所以：**沙箱不是保险箱。** 业务代码仍要守规范。

## 对照上单 2.0：哪些是沙箱做的，哪些是你们做的

| 问题 | 谁解决 | 你们怎么做的 |
|------|--------|--------------|
| 子应用乱改 window | qiankun Proxy 沙箱 | 开默认沙箱即可 |
| Vue2 iView 和 Vue3 antd 样式互污染 | Shadow DOM（strictStyleIsolation） | 方案里显式打开 |
| 弹窗挂 body 丢样式 | 沙箱解决不了 | 弹窗 `getPopupContainer` 挂到子应用根节点；或不用 strict，改用 scoped / 约定前缀 |
| 切走后 eventBus 还在听 | 沙箱不管 mitt | `beforeUnmount` 里 `window.$mittEventBus.all.clear()` |
| Pinia 脏数据（进下一个项目还是上一个） | 沙箱不管应用内部 store | unmount 时 `app.unmount()`，进页重新拉接口，不要复用旧 store |
| 浅拷贝改销售计划开售时间 | 跟沙箱无关 | 业务层深拷贝，别改源数据 |

面试官问「你怎么解决微前端沙箱问题」，不要答「我们用了 qiankun 所以没问题」。正确切法是：

**框架隔离 JS/CSS；卸载和第三方弹窗靠约定补。**

## 面试 60 秒（够用，不要展开源码）

微前端核心问题是主子应用共一个浏览器上下文，JS 和 CSS 会互相污染。iframe 隔离最干净，但弹窗和路由体验过不去。

我们用 qiankun：JS 侧用 Proxy 给子应用假 window，卸载时还原；样式侧开了 `strictStyleIsolation`，走 Shadow DOM。定时器和动态样式表 qiankun 会劫持，卸载时清。

沙箱覆盖不了的，我们自己收：卸载清 eventBus；antd 弹窗挂到子应用容器而不是 body；业务 store 不跨项目复用。组里贾顺昌分享过 Snapshot / Proxy / Shadow DOM 的利弊，结论就是强隔离有改造成本，所以上单是沙箱 + 规范一起用。

## 对方追问怎么接（只准备这 4 个）

**Snapshot 和 Proxy 差在哪？**

Snapshot 改真 window，走时还原，单实例。Proxy 假 window，可多开。现代浏览器走 Proxy。

**Shadow DOM 为什么还样式乱？**

弹窗、message 挂在 body 上，不在 Shadow 里。这是强隔离的经典洞，不是没开沙箱。

**能不能关 Shadow DOM？**

能。关了改用 CSS 前缀 / scoped，隔离变弱，主子样式可能互影响。上单选强隔离，是因为 Vue2 和 Vue3 两套组件库必须硬切开。PPT 原话：不用 Shadow 就不能保证子应用不受主应用和其他子应用影响。

**沙箱逃逸举一个？**

改 `window.xxx` 能拦；改 `window.xxx.yyy` 拦不住。所以规范是：子应用禁止往 window 挂业务状态，通信走 props / 主应用注入的 eventBus，并且 unmount 必清。

分享看不懂，通常卡在「假 window」这三个字。用一句话建立直觉：

**子应用里的 window 不是浏览器那个，是 Proxy 拦下来的替身；样式不在页面根上，而在一块 Shadow 里。卸载 = 扔掉替身、拆掉 Shadow、清掉定时器和事件。**

先把这句话和「弹窗挂 body 会逃出 Shadow」背熟。源码可以以后再看。
