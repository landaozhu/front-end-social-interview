模块联邦（Module Federation）是 Webpack 5 的运行时模块共享：一个应用当 **Host**，运行时去拉另一个应用 **Remote** 暴露出来的模块，像 `import` 本地文件一样用，不必把对方整站打进自己的包。

上单没用它，用的是 qiankun。面试要能说清 **它是什么、和 qiankun 差在哪、为什么当时不选**。

## 它在解决什么

微前端要「独立开发、独立部署、运行时组合」。模块联邦走的是 **构建产物级共享**：

| 角色 | 干什么 |
|------|--------|
| Remote | `exposes` 把页面/组件/工具函数暴露出去，生成 `remoteEntry.js` |
| Host | `remotes` 声明去哪拉，运行时请求 remoteEntry，再加载具体模块 |
| shared | `vue` / `react` 等声明单例，避免两套运行时 |

和 `externals` 的差别：externals 是「别打进来、去全局找」；模块联邦是「运行时按模块图去远程拿」，还能共享版本策略。

## 和 qiankun 怎么对比（25k 够用）

| | 模块联邦 | qiankun |
|--|--|--|
| 接入物 | JS 模块（webpack 图） | **HTML Entry**（整页 html/js/css） |
| 子应用约束 | 基本要 Webpack 5 + 配 MF | 不限框架，有约定的生命周期就行 |
| 依赖去重 | `shared` 原生支持 | 多靠 externals / 主应用先加载 |
| 沙箱 | 不负责 JS/CSS 隔离 | Proxy 沙箱 + 可选 Shadow DOM |
| 典型场景 | 同构、都已 webpack5、要组件级复用 | 存量系统渐进拆、Vue2/Vue3 混跑 |

一句话：模块联邦是 **打包器能力**；qiankun 是 **运行时微前端框架**（加载、沙箱、生命周期）。

## 上单为什么没用

上单 2.0 是 Vue2 老系统渐进迁 Vue3，子应用技术栈不齐，要的是 **整页接入、独立部署、隔离要强**。

- 模块联邦要求子应用都按 MF 改 webpack，存量迁移成本高（选型结论原话就是这个）
- qiankun HTML Entry：子应用还是自己的入口 html，主应用 `loadMicroApp` 就能挂
- Vue2 iView 和 Vue3 antd 必须硬切开样式 → 更吃 qiankun 的 `strictStyleIsolation`，MF 不管沙箱

所以不是「模块联邦不行」，是 **当时约束下 qiankun 更贴存量**。新项目、全员 webpack5、要跨应用抽组件，MF 更合适。

## 面试 60 秒

Webpack 5 模块联邦让 Host 在运行时加载 Remote 暴露的模块，用 shared 去重公共依赖。它解决的是模块共享和独立部署，不管 JS/CSS 沙箱。

我们上单选 qiankun 不选它：老系统 HTML Entry 接入便宜，且 Vue2/Vue3 两套组件库要强隔离。模块联邦更适合已经统一在 webpack5 上、要组件级复用的团队。

## 追问

**remoteEntry.js 是干什么的？**

Remote 的清单：有哪些 exposes、shared 怎么协商。Host 先拉这份，再按需拉具体 chunk。

**shared 版本冲突怎么办？**

配 `requiredVersion` / `singleton`。对不上会重复加载或启动失败，所以 MF 对基建纪律要求比 qiankun 高。

**Vite 能用吗？**

能，但不是 Webpack 那套插件，要用兼容方案（如 `vite-plugin-federation`）。上单是 webpack5，这题点到即可。

**和 iframe 比？**

iframe 隔离最干净，弹窗和路由体验差。MF 和 qiankun 都在同一页里组合，体验好，隔离要自己做。
