# 对 React 架构演进了解吗？

25k 一面过关线：能按 **15 → 16 Fiber → 17 渐进 → 18 Concurrent** 说出 **每一代在解决上一轮的哪一个痛**；追问能分清 **Fiber 是可中断的基础，18 的 `createRoot` 才把 Concurrent 打开**。只背「有 Fiber、能打断」或把 [更新原理](./react更新原理.md) 整条链再背一遍，过不了。

本题讲 **为什么改架构**。一次更新怎么走完，看更新原理；18 新 API 看 [react18更新了什么](./react18更新了什么.md)。

---

## 开口（40 秒）

React 的架构不是一次设计完的，是 **主线程被卡住之后，一代一代把「能不能停、谁先画」补上**。

15 用调用栈递归 diff，树一大，输入和动画都要等它走完。16 把树改成 Fiber 链表，工作可以在节点之间让出主线程，这是后面所有可中断的前提。17 几乎不改架构，把事件委托收到 root，方便渐进升级。18 用 `createRoot` 打开 Concurrent：可打断的 render、自动批处理、`startTransition` 低优更新。还在用 `ReactDOM.render`，18 的这条路没开。

---

## 每一代在解决什么

| 版本 | 架构关键词 | 上一轮的痛 | 换来什么 |
|------|------------|------------|----------|
| **15** | Stack Reconciler | jQuery 式改 DOM 难维护 | 虚拟 DOM + 递归 diff，心智简单 |
| **16** | Fiber | 递归一开就不能停，长列表卡输入 | 链表单元、双缓冲草稿、Error Boundary |
| **17** | 渐进升级 | 大版本难跳 | 事件挂到 root，不逼你一次升完 |
| **18** | Concurrent | Fiber 有了，默认仍几乎同步刷完 | `createRoot`、自动批处理、Transition、Suspense 更好用 |

15 的问题是 **算法在调用栈上**，函数没返回，浏览器插不进输入。Fiber 把「做一个组件」变成循环里的一步，可以停。但 16/17 默认仍是尽快把这棵树做完，用户感知更像「不太卡」，不是完整 Concurrent。

18 才把调度优先级和可丢弃的低优 render 当成正式能力。所以面试说「16 就能打断」要补一句：**能力在 16 铺好，产品化在 18，还得换 API。**

---

## 别和更新原理混成一道

- 问 **演进**：按版本讲痛点和为什么改，停在上表。
- 问 **一次 setState 怎么走**：调度 → render 草稿 → commit，见更新原理。
- 问 **18 有什么 API**：`createRoot`、自动批处理、`startTransition`，见 react18。

双缓冲、优先级、commit 不可中断，都是 Fiber 之后同一条链上的机制，演进题点到「为了可中断才拆成这样」即可，不要把更新原理整段搬过来。

React 19 的 Compiler 想自动 memo，减少手写 `useMemo`。一面知道「还在演进、编译期补运行时」就够，没上过生产不要装熟。

## 追问

- **Fiber 解决了 15 的什么？** 递归栈不可打断。改成链表工作循环，主线程能在节点之间回去处理输入。
- **16 有 Fiber，为什么还要 18？** Fiber 是地基；18 才默认打开 Concurrent 调度、批处理和 Transition。入口是 `createRoot`。
- **17 没架构为啥算一代？** 为了让 15/16 项目能渐进接到 18，事件系统改挂载点，减少一次升级炸全站。
- **半成品会不会上屏？** 不会。演进到 Fiber 就是为了草稿可扔；commit 才改 DOM。细节走更新原理。
- **和 Vue 比？** Vue 走依赖收集 + 编译优化，没有这套 Concurrent 打断。别把 `nextTick` 说成 Fiber。
