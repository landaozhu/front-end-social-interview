# 灰度环境怎么做的（50% 机制）？

【一句话】**同一入口，网关按规则把一部分流量打到灰度桶。** 50% = 用户标识 hash 后取模，一半进灰度、一半走主干；前后端必须同桶。

## 50% 怎么分流

```
uid / cookie / IP → hash → hash % 100
  < 50  → 灰度静态资源 + 灰度 Node / 接口
  ≥ 50  → 主干
```

要 **sticky**：同一用户一直在同一桶，不能刷新就跳。用 uid 或灰度 cookie，不要纯随机每次请求。

## 内灰 vs 外灰（猫眼 order-h5）

| | 内灰 | 外灰 |
|---|---|---|
| 谁进 | 开发/测试带 `isshowgray=true` | 真实用户按百分比 |
| 目的 | 正式环境验功能 | 放量看错误率和转化 |
| 风险 | 人少 | 有真实钱和票 |

存量 peon 网关不支持灰度 → 迁 WebStatic，oceanus 配路径。前端把灰度标识传后端，**避免前端灰度、后端主干**。

放量：1% → 10% → 50% → 100%。出问题降到 0 或切回主干，比回滚整包快。

## 追问

- **静态资源和接口？** 都要跟桶走，否则 JS 是新的、接口是旧的。
- **SSR？** 网关在进 Node 前分流，这台 Node 只打灰度包。
- **为什么先迁网关？** 没分流能力就只能全量，出事就是线上事故。
