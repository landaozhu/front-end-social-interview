# 选座页性能优化怎么做的？首屏 2s 到 1.3s？

## 考察点

- 是否**先度量再优化**（20k 必备）
- 能否说具体手段，而非只答「懒加载、分包」
- 能否解释 H5 + 小程序两侧差异

---

## 30 秒版

先定位瓶颈：首屏**串行接口**和**大包阻塞**。手段：**接口并行化、分包、按需加载**减少首屏 JS 和网络 waterfall。优化后新选座页首屏从约 **2s 到 1.3s，下降 50%+**。用真机和业务场景验证，不是只看开发者工具。

---

## 2 分钟版

### 1. 度量（先问再做）

- Network：首屏接口是否串行等待  
- Performance：JS 解析执行、大包下载时间  
- 业务埋点 / 真机：弱网、低端机  
- 对比对象：**优化前后同一选座页**，不是和其他页比

### 2. 关键优化点

| 优化 | 解决什么 | 原理 |
|------|----------|------|
| **串行改并行** | 多个接口依次等 | 无依赖的请求 Promise.all / 同时发出 |
| **分包** | 主包过大 | 座位图等非首屏模块拆分包，按路由加载 |
| **按需加载** | 首屏 JS 过多 | 非关键组件 dynamic import |
| **资源** | 图片/CDN | 座位图合适尺寸、CDN（配合团队规范） |

### 3. 小程序侧额外注意

- **主包 2M 限制** → 分包策略更严格  
- **setData 成本** → 座位图避免一次 set 全量数据  
- **双线程** → 逻辑层和渲染层通信有开销  

### 4. 与 webpack 升级的关系（若被问）

order-h5 项目 webpack 2→4：  
- 首次编译 **50091ms → 21286ms**  
- 热更新 **14691ms → 3749ms**  
- 原则：**构建变快，页面 Lighthouse 性能基本不变**（升级时用 lighthouse 对比 seat-area、select-seats 等页）  
- 踩坑：升级手势库未验证导致无法缩放；sourcemap 误上线上导致包变大 → CDN 迁移+拆包解决  

选座页本身优化和编译优化是**不同维度**，但团队整体迭代更快。

### 5. 验证与回滚

- 固定测试项目和场次 id  
- 真机 + 弱网  
- 灰度发布验证（团队灰度体系）  
- 指标回退则回滚静态资源版本  

### R — 结果

首屏 **2s → 1.3s**；后续固定套票、复杂票型可在同一架构扩展。

## 常见追问

**Q：为什么不用 SSR？**  
A：选座页强交互、强登录态，座位图客户端渲染为主；优化重点是**接口并行和包体积**，SSR 收益和改造成本不匹配这个场景。

**Q：并行会不会给后端压力？**  
A：首屏本来就要这些数据，并行只是**缩短等待**，不是增请求；若有限流和后端对齐过 QPS。

**Q：还能怎么优化？**  
A：接口聚合（BFF）、座位图 WebWorker/分片渲染、预加载下一屏资源——要再 profiling 看瓶颈。
