# uni-app 熟悉吗？和原生小程序怎么选？

## 考察点

- 是否理解 uni-app **是什么、解决什么问题**
- 选型有没有**业务视角**，不是「我会用 uni-app」
- 兼容题能不能**诚实答维护级**，不装框架专家  

> **宏波**早期接触过 uni-app 移动办公，**一笔带过即可**；主答**认知 + 选型 + 兼容处理思路**。

---

## 30 秒版（主背 — 基于你的版本）

我用过、了解 **uni-app**。它本质是用 **Vue 的开发方式**，通过编译适配到微信/支付宝小程序、H5、App 等多端。

**选 uni-app 还是原生小程序**，我看四点：**业务复杂度、性能要求、平台能力依赖、多端复用价值**。

- 业务比较标准（商城、活动页、表单、会员中心），且明确要多端（微信+支付宝+H5）→ 倾向 **uni-app**，一套代码复用逻辑，成本更低。  
- 强依赖微信原生能力（复杂地图、直播、音视频、Canvas、WebGL、极致分包），或交互/性能要求高 → 倾向 **原生小程序**，链路短、API 跟得紧、排查成本低。  

**核心**：不是 uni-app 一定更好，而是**跨端收益能不能盖住适配成本**。若 90% 流量在微信，只为「以后可能做支付宝」上 uni-app，反而多一层框架和兼容维护。

## 2 分钟版

### 1. uni-app 是什么

| 维度 | 说明 |
|------|------|
| 开发 | Vue 语法写 `.vue`，用 `view`/`text` 等标签 |
| 编译 | 各端编译器生成目标平台代码（小程序 → wxml/wxss/js） |
| API | `uni.xxx` 统一封装，需查**各端支持差异** |
| 差异 | `#ifdef MP-WEIXIN` 等**条件编译**处理端差异 |

**一句话**：用 Vue 经验快速出多端，中间多一层**编译 + 运行时适配**。

---

### 2. 什么时候选 uni-app（你的判断标准）

**适合**：

- 页面以**列表、表单、活动、会员**为主，交互标准  
- **明确**要同时维护微信、支付宝、H5 等，复用价值高  
- 团队 **Vue 栈**，人力有限，不想多套代码  
- 性能要求「够用」，不是毫秒级极致  

**不适合 / 慎用**：

- 强依赖**单平台深度能力**（直播、复杂地图、Canvas/WebGL、重度分包优化）  
- **核心交易链路**，性能、稳定性、包体积极敏感  
- 实际流量**集中在一个端**，却为「也许以后多端」提前引入 — **适配成本 > 收益**  

**对比表**：

| | uni-app | 原生小程序 |
|---|---------|------------|
| 跨端 | 强，一套逻辑多端发 | 弱，基本单端 |
| 性能/链路 | 多一层编译与适配 | 最短 |
| 平台新能力 | 往往滞后，等框架跟进 | 官方第一时间 |
| 排查 | 可能要区分是框架问题还是业务问题 | 相对直接 |
| 团队 | Vue 友好 | 要学 WXML/小程序规范 |

**和 Taro**：React 团队跨端更常选 Taro；Vue 团队更常选 uni-app — 都是**用框架换复用**，选型看团队栈。

### 3. 兼容问题怎么处理（了解 + 维护级，不装深）

uni-app 面试常问兼容 — 我按**维护经验**答，不背源码。

**原则三板斧**：

1. 查官方 **API 各端支持表**  
2. 不支持 → **条件编译** 或换实现  
3. **真机验证**（工具里键盘、安全区、滚动经常不准）

**高频兼容点**（记类别即可）：

| 类别 | 常见坑 |
|------|--------|
| **样式** | rpx；iPhone **safe-area** 挡底部按钮；fixed + 键盘顶起乱飞 |
| **API** | `uni.login` 各端不同；`navigateTo` **页面栈 10 层**；`storage` 有大小限制 |
| **滚动** | `scroll-view` **必须设高度**，否则滚不动 |
| **富文本** | 小程序不支持完整 HTML，`rich-text` / web-view 有限制 |
| **组件库** | 版本要和编译器匹配，升级先看 changelog |

**条件编译示例**：

```javascript
// #ifdef MP-WEIXIN
// 仅微信
// #endif

// #ifdef H5
// 仅 H5
// #endif
```

**真机**：样式、键盘、上传、picker — **至少 iOS + Android 各点一遍主流程**。

**性能（维护级，不吹架构）**：列表分页、图片压缩、少在 onShow 重复请求、storage 别塞大对象。深度优化（分包预下载、setData 级）更常出现在**原生/C 端交易**场景。

### 4. 我的经历（宏波只提一嘴）

早期在**内部办公小程序**接触过 uni-app 维护（表单、列表类页面），对**条件编译、真机兼容、uni API 差异**有实际感受。

近期小程序经验主要在**猫眼演出 H5/微信侧页面开发**（非 uni-app 栈），所以对「**什么时候该用 uni-app、什么时候该原生**」体会更深 — 交易类页面不会为了跨端强行上 uni-app。

## 常见追问

**Q：uni-app 原理了解吗？**  
A：了解层面：Vue 单文件 → 编译到各端语法 + `uni` 运行时做 API 适配。没深入改过编译器，日常靠文档和条件编译解决问题。

**Q：rpx 是什么？**  
A：响应式单位，规定屏宽 750rpx，随屏幕缩放；小程序/uni-app 里对齐设计稿常用。和 rem（相对根字体）不是一套体系。

**Q：真机和开发者工具不一致？**  
A：**以真机为准**。工具对键盘、安全区、滚动模拟不准，发版前必真机过主流程。

**Q：uni-app 和原生你更熟哪个？**  
A：**原生/业务页面开发**更熟（猫眼）；uni-app 是**了解 + 早期维护过**，选型问题上可以聊，不会包装成 uni-app 专家。

**Q：如果项目已经用了 uni-app，你怎么上手？**  
A：先看 `pages.json` 路由和分包；查项目用的 **UI 库和 uni 版本**；改功能前查 API 支持表；动样式和跳转必真机；不确定的端差异用 `#ifdef` 隔离。

**Q：为什么你们没用 uni-app 做选座？**（若被问）  
A：选座重交互、性能、包体积，还涉及复杂页面能力 — 用**原生/定制链路**更合适，和上面选型标准一致，不是 uni-app 不好，是**收益盖不住成本**。

## 不要说的

| ❌ | ✅ |
|----|-----|
| 「uni-app 比原生都好」 | **看业务，看跨端收益是否盖住成本** |
| 宏波 5000 人、组长、审批展开讲 | **早期内部办公维护过一嘴** |
| 「精通 uni-app 原理/性能架构」 | 了解 + 维护级兼容处理 |
| 背 nvue、renderjs 没用过 | 知道是 App 端增强，生产未深入 |
| 假装 H5/App/支付宝全都上过 | 按实际接触说，主答选型逻辑 |
