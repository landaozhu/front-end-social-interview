# 为什么选 qiankun 微前端？踩过什么坑？

## 考察点

- 架构选型 reasoning，不是「公司让用」  
- 微前端真实坑和边界

---

## 30 秒版

上单系统**不能一次性重写**，要渐进迁移。qiankun 基于 Vue 栈，比 iframe 体验好，支持子应用**独立部署**。我参与调研和评审，主应用管路由/登录/布局，子应用管业务域。坑：**样式隔离、子应用卸载污染、跨应用通信、路由切换状态残留**。

---

## 2 分钟版

### 为什么需要微前端？

| 痛点 | 微前端解决 |
|------|-----------|
| 老上单 Vue2 耦合 | 新模块 Vue3 独立开发，逐步替换 |
| 发布风险 | 子应用独立发版，不全量 rewrite |
| 多团队 | 业务域边界清晰 |

### 为什么 qiankun？

- 团队 **Vue 为主**，qiankun 生态成熟  
- HTML Entry 接入成本低，适合存量系统  
- 对比 iframe：SEO/体验差；对比 Module Federation：迁移成本更高  

### 架构分工

- **主应用**：路由、登录、菜单（userMenu）、布局  
- **子应用**：条件退、销售计划、场次管理等域  
- **通信**：尽量走 URL + 后端状态，减少 global 事件耦合  

### 踩坑

1. **样式隔离**：antd-vue 全局样式泄漏 → 严格 scoped + 主应用样式规范  
2. **卸载残留**：切换子应用 global 变量/eventBus 未清 → 制定卸载 checklist  
3. **路由同步**：主子路由前缀一致，避免 404 和重复 history  
4. **首屏 userMenu**：原串行阻塞首屏 → html 预请求 userMenu（见 26 题，约 400–500ms）  
5. **TS 类型**：跨应用共享类型放 npm 包或 monorepo  

### 你的角色

- 参与**技术选型评审**，不是只写子应用  
- 负责模块在子应用内落地，联调 Egg 中间层  

---

## 常见追问

**Q：不用微前端行不行？**  
A：全量 rewrite 周期长、风险大；业务等不起。微前端是**工程上的折中**。

**Q：和 monorepo 区别？**  
A：微前端强调**独立部署/runtime 集成**；monorepo 是代码组织。我们既要独立发版又要统一入口。
