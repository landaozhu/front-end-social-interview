# 线上 P0 故障怎么处理？

## 考察点

- 是否知道 P0 **第一目标是恢复业务**，不是先炫技术定位  
- 会不会**同步信息、拉上下游**  
- 修复后有没有**验证 + 复盘**意识  

> 通用题，按流程答；不必绑具体项目。

---

## 开口版（约 45 秒，主背这版）

如果是线上 P0，我**第一目标不是马上找根因，而是尽快恢复核心业务、控制影响面**。

**第一步**，快速确认**故障现象和影响范围**——全量还是部分用户、核心链路完全不可用还是某个功能异常；同时**同步负责人和上下游**，避免信息不同步。

**第二步，优先止损**。若和**刚发的版本**高度相关，我一般不会先花大量时间抠代码，而是优先**回滚、关功能开关、降级或切兜底**。比如新版本导致核心页白屏，只要和发布强相关，**先回滚到上一稳定版本**，把业务恢复再说。

**第三步**，业务恢复后，再结合**监控和日志**定位根因。前端我会看错误监控、接口成功率、JS Error、白屏率、资源加载失败、用户行为链路，并对照**发布记录和 Git diff**。涉及接口、网关、CDN 或服务端，会及时拉对应同学一起查。

**第四步**，修复后**不会直接全量**。先在测试环境验证，再**灰度发布**，观察错误率和核心业务指标，稳定后再逐步放量。

**最后**一定做**复盘**：时间线、影响范围、根因、为什么监控/测试没拦住，以及后续 Action Item（补告警、灰度、发布 Checklist、异常兜底等），避免同类问题再发生。

---

## 极简版（30 秒）

**先恢复业务再查因**：确认影响并同步 → 能回滚先回滚止损 → 恢复后看监控和发布 diff 定位 → 测试/灰度验证后再放量 → 复盘留改进项。

---

## 2 分钟版（按你的思路展开）

### 1. 目标：恢复业务，控制影响面

P0 和日常 bug 不同：

| | P0 | 普通 bug |
|---|-----|----------|
| 第一目标 | **用户先能用** | 可以排期修 |
| 定位 | 止损**之后**再做 | 可以边查边修 |
| 发布 | 修完也要**验证再放量** | 走正常节奏 |

**不对的说法**：「我先本地复现慢慢查。」  
**对的说法**：「我先确认影响面，能回滚就先回滚。」

---

### 2. 确认现象 + 同步（和止损并行）

**要搞清楚的**：

- **现象**：白屏、下单失败、按钮无反应、数据大面积错误……  
- **范围**：全量 / 部分地域 / 部分端（H5、小程序）/ 部分功能  
- **时间**：大概从什么时候开始  
- **是否和发布相关**：最近有没有发版、改配置、开关、活动  

**同步谁**：直属负责人、值班、相关前后端/测试/运维 — 群里一句话说清：**现象 + 影响 + 谁在处理 + 当前动作**。

---

### 3. 止损（优先于深度定位）

**原则**：和**刚发布强相关**时，**先回滚/开关/降级**，不在火线上大改。

| 手段 | 什么时候用 |
|------|------------|
| **回滚**上一稳定版本 | 发版后短时间内出问题 — 最常见 |
| **关功能开关** | 非核心能力可先关，保主链路 |
| **降级 / 兜底** | 有旧页面、旧接口、静态兜底页 |
| **停灰度 / 切回主干** | 新版本有问题，小流量先掐掉 |

**例子（通用）**：新版本导致核心页白屏 → 确认和发布相关 → **先回滚**，业务恢复后再查是哪次提交引入的。

**避免**：多人同时改、未验证就再全量、在 P0 窗口做大重构。

---

### 4. 业务恢复后：定位根因

止损完成、指标开始回落后，再**系统性查因**。

**前端常看**：

- 错误监控（如 Sentry）、JS Error、白屏率  
- 接口成功率、超时、5xx  
- 静态资源 404、chunk 加载失败  
- 核心埋点 / 用户行为链路是否断崖  
- **发布记录 + Git diff**：最近改了什么  

**协作**：若像接口、网关、CDN、服务端问题，**及时拉对应同学**，不先甩锅也不单扛。

**输出**：能说出「直接原因 + 触发条件」，为修复和复盘做准备。

---

### 5. 修复：测试 → 灰度 → 再全量

P0 修完**不能直接全量**，否则容易**二次事故**。

1. **测试 / 预发**：走一遍核心路径（进首页、关键按钮、提交/下单等）  
2. **灰度 / 小流量**：看错误率、接口成功率、业务指标  
3. **稳定后再逐步放量**，并持续观察一段时间  

改动原则：**最小修复**，不顺手重构；hotfix 也要自查和评审，但可以走**加急流程**。

---

### 6. 复盘（必做）

复盘要对事，产出**能落地的 Action Item**：

| 复盘项 | 问什么 |
|--------|--------|
| 时间线 | 何时发现、何时止损、何时完全恢复 |
| 影响范围 | 多少用户、哪些功能、持续多久 |
| 根因 | 技术直接原因 + 流程上为何没拦住 |
| 监控 | 为什么没提前告警 |
| 测试 | 为什么没拦住 |
| **Action Item** | 补监控告警、灰度能力、发布 Checklist、异常兜底、自动回滚等 |

**对面试官**：体现你不只「修完了」，还思考**怎么防止再来一次**。

---

## 一句话总结

> **先恢复、再查因；能回滚先回滚；修完灰度验证；最后复盘留项。**

---

## 常见追问

**Q：回滚和 hotfix 怎么选？**  
A：和刚发版强相关、回滚能立刻恢复 → **先回滚**。回滚解决不了或老版本也有问题 → 再 **hotfix**，且必须测试/灰度后再上。

**Q：怎么判断是不是前端问题？**  
A：看浏览器/小程序报错、资源 404、是否仅前端发版后出现；但保持开放，用时间线和日志一起定，该拉后端就拉。

**Q：一个人搞不定怎么办？**  
A：及时升级负责人和上下游，P0 目标是**最短时间恢复业务**，不是一个人扛到底。

**Q：你实际处理过吗？**  
A（诚实、通用）：  
> 「线上问题按这个流程参与过，具体业务不同，但**先止损、再同步、再定位**的顺序是一样的。」  
不夸大主 R，被追问再说参与哪一环（排查 / 回滚 / hotfix / 观察）。

---

## 不要说的

| ❌ | ✅ |
|----|-----|
| 「我先本地慢慢复现」 | 先确认影响，优先止损 |
| 只讲查代码，不讲同步和复盘 | 恢复 → 定位 → 验证发布 → 复盘 |
| 修完直接全量 | 测试 / 灰度 / 看指标再放量 |
| 堆具体项目、系统名 | 用回滚、开关、灰度等通用词 |
| 复盘变成甩锅 | Action Item 对事 |
