# Code Review 怎么推动？

## 30 秒版

猫眼参与**技术中心前端 CR 规范**：自查(lint+注释) → **2 人 Review** → 测试提测 → 合 Release 再审 → 发布审核 → 合 master 3 人。我实践全流程，5–10 PD 写技术方案，>10 PD 拉会。结合 **eslint + AI 辅助**自查，Review 聚焦逻辑/发布风险而非缩进。

## 2 分钟版

**流程**  
1. 技术评审：5–10 PD 文档，>=10 PD 文档+会  
2. 自查：lint、每文件注释/PR 说明、高风险操作标注  
3. 提测前：draft PR、2 approve、测试可打回  
4. 合 Release：只查逻辑事故（删 console 可能是大问题）  
5. 发布审核：2 approve + 无打回 + 符合方案  
6. 合 master：3 人确认无新增代码  

**评审人选择**  
- 前端主 R > 熟悉提交记录的人 > 模块分工（商家端/交易/端负责人）  

**延时机制**  
- 评审不过 → 延到下一发布周期，不占用评审人时间  

**我推动什么**  
- 组内按规范执行 PR 模板  
- eslint 插件减少低级 error，Review 看业务  
- 上单条件退 bug 复盘 → **自测 checklist** 减少 Review 轮次  

**20k 价值**  
- 不是「爱 Review」，是**用机制降事故**
