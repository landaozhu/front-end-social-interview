# 范特西新上单 2.0 项目介绍

## 考察点

- B 端复杂业务 + 架构升级 — 20k 核心项目
- 能否讲清**为什么重构、你负责什么、技术选型**

---

## 30 秒版

演出 B 端**核心录单系统**重构。旧系统 Vue2、耦合高，难支持场次/蓄水/巡演。选型 **qiankun + Vue3 + TS + webpack5 + Egg**，微前端模块化拆分。我参与选型评审，负责**条件退、销售计划**模块，处理**蓄水**状态切换，并用 **Egg** 改部分中间层加速联调。

---

## 2 分钟版

### S — 背景

- 演出扩展 → 上单流程复杂化（场次、蓄水、巡演、条件退）  
- 历史依赖旧、模块耦合 → 新需求开发和维护成本高  
- 目标：模块化拆分 + 统一架构，支撑后续迭代  

### T — 技术栈与职责

| 层级 | 技术 |
|------|------|
| 前端 | qiankun、Vue3、TS、webpack5、ant-design-vue |
| 中间层 | Egg.js（部分重构） |
| 个人模块 | 条件退、销售计划、蓄水联动、录单交互优化 |

### A — 架构

- **微前端**：按业务域拆子应用，老系统渐进迁移  
- **Vue3 Composition**：状态密集模块 composable 化  
- **TS**：与后端接口对齐，减少联调返工  
- **Egg**：部分 mapi/中间层自己改，不等后端排期  

### 业务复杂度（体现深度）

**条件退**  
- 项目限退、场次限退、退票政策、订单批次  
- 绝对时间 vs 相对时间（每场开演前/当天/订单相对时间）  
- 审核前/后、蓄水/立即开售/定时开售 → **开关能否关闭**规则不同  
- 同一批次同一场次退票时间段不可重合  

**销售计划**  
- 与场次增删改、复制联动  
- 审核通过前后：草稿 vs 读库，离开页是否拦截  
- 自定义可预约、可售、可见场次级联  

**蓄水**  
- 非蓄水转蓄水限制、渠道校验、条件退拦截  
- 与售卖状态、审核状态交叉  

### R — 结果

- 新需求开发和维护成本下降  
- 后续页面有统一架构基础  
- 个人延伸 Node 中间层能力
