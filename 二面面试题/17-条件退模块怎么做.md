# 条件退模块怎么做的？复杂逻辑怎么保证质量？

## 考察点

- B 端复杂表单 + 状态机 — 20k 深度题
- 能否讲测试和 bug 复盘（wiki 有大量真实 case）

---

## 30 秒版

条件退是上单 2.0 **履约核心**：项目限退、场次限退、退票政策、订单批次。难点是**时间类型混搭**（固定/每场开演前/当天/订单相对时间）、**审核前后规则不同**、与蓄水/销售计划联动。我用**分层表单 + 自定义校验 + 自测 checklist** 保证质量，bug 复盘后沉淀了置空、边界、tab 切换等 case。

---

## 2 分钟版

### 模块结构

1. **项目限退**：开关 + 规则配置；审核通过且已开售可能**禁止关闭**  
2. **场次限退**：按场次配置规则；默认规则 vs 规则1、规则2…  
3. **退票政策**：名称、批次、开始/截止时间、手续费（比例/固定金额）  
4. **批次管理**：订单批次名唯一性、空批次校验  

### 核心逻辑（举例说明深度）

**时间校验**  
- 绝对时间：开始 ≤ 结束  
- 相对时间：依赖「应用场次」计算，未选场次无法算绝对时间  
- 订单相对时间：开始/结束必须同为订单相对，否则黄色提示  
- 混搭：一个固定一个相对 → 可比较则红色提示  

**重合校验**  
- 同一订单批次 + 同一场次 → 退票时间段不可重合  
- 不同批次或不同场次 → 允许  

**审核状态 × 售卖状态**  
- 待提交：条件退开关可关  
- 审核通过 + 立即开售：可能禁止关闭  
- 审核通过 + 定时开售：开售前可关，开售后禁止  
- 蓄水场景：另有拦截（见 19 题）  

**默认规则**  
- 第一个规则为默认；场次删光时规则1升默认；编辑时「全选场次」在新建/编辑场景文案不同  

### 质量保障

- 50+ bug 复盘分类：置空、PRD 不清、深拷贝误改 store、组件 API 不熟  
- 自测清单：表单校验、自定义校验、切换选项提示消失、高频点击防重复提交  
- 错误提示**滚动定位**到字段（UX 细节）  
- 1.0 → 2.0 数据兼容：旧场次限退要在新页展示  

### 典型 bug 教训

**销售计划 tab 切换改坏开售时间**  
- 原因：判断条件退是否可关时，**浅拷贝改写了 store 开售时间**  
- 修复：判断用深拷贝，禁止改源数据；全量自查类似写法

## 常见追问

**Q：这么复杂为什么不用规则引擎？**  
A：业务仍在快速迭代，规则引擎引入成本高；当前用**纯函数校验 + 单测关键规则**更务实；长期可抽配置。

**Q：和后端分工？**  
A：前端拦截 + 体验；最终保存后端兜底；重复校验保证一致性。
